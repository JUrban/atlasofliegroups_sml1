# REPORT_260501 — Atlas `.at` → SML replacement + staged HOL4/CakeML verification

Date: 2026-05-01  
Repo root: `/project`

## Executive summary (where the project stands today)

This repository contains the Atlas C++ library (core representation theory and Lie-theoretic computations) together with the classic Atlas `.at` interpreter and script library (`atlas-scripts/`). The project goal has been to **replace execution of `.at` scripts with Standard ML (Poly/ML)**, while continuing to use the Atlas C++ implementation for the heavy semantic primitives (groups, parameters, unitarity checks, etc.). The replacement must be runnable as **SML code** that depends only on the C++ library via an SML-facing API/FFI layer, not on the Atlas interpreter and not on `.at` scripts at runtime.

The project has reached a substantial milestone:

- The most important script, `atlas-scripts/script_to_verify_F4_FPP_unitary_dual.at`, is replaced by an SML entry script:
  - `atlas-scripts-sml/script_to_verify_F4_FPP_unitary_dual.sml`
  - which runs the driver `atlas-scripts-sml/VerifyF4FPP.sml`.
- Running:
  - `bash atlas-scripts-sml/ffi/build.sh`
  - `poly -q < atlas-scripts-sml/script_to_verify_F4_FPP_unitary_dual.sml`
  computes the expected **F4_s** verification set (size **1864**) and executes a bottom-layer check suite (standard/final, lambda-table consistency, twist equivalence, hermitian/unitary, and contragredient closure).
- The slow completeness checker (originally a multi-hour `.at` script) has an SML translation:
  - `atlas-scripts-sml/SimplerVerifyF4FPP.sml` + entry script `atlas-scripts-sml/simpler_script_to_verify_F4_FPP_unitary_dual.sml`
  and includes a bounded sampling mode (`runFast`) intended for ≤5 minute partial checks.
- A **formal verification scaffolding** exists in HOL4 with a companion CakeML “translator playground”. The emphasis so far has been to make the *end-to-end statements and their refinement structure explicit*, isolating the truly hard parts (FFI semantics, program-success bridges, and the imperative hash-table invariants) behind named obligations that can be gradually discharged. The repository keeps a precise inventory of what is currently `CHEAT`-tainted and why.

In addition to the F4/FPP verification pipeline, the SML side now contains a growing body of **pure combinatorics** ports (classical nilpotent orbits via partitions, Springer correspondence building blocks for types B/C/D, symbol/bipartition conversions, etc.), designed to be reused by other `.at` translations without needing interpreter infrastructure.

This report is a consolidated technical description of:

1. the SML replacement architecture (FFI and module structure),
2. the main F4/FPP verification workflow in SML (fast and slow programs),
3. the approach to translating `.at` scripts into idiomatic-but-literal SML,
4. the staged HOL4/CakeML verification plan (top-level theorems, refinement layers, remaining bridge obligations),
5. what has been completed, what remains, and the main known risks/unknowns.

## 1. Project goal and non-goals

### 1.1 Primary goal

Replace the Atlas `.at` interpreter layer with Standard ML programs that:

- are “script replacements” for key `.at` files,
- can be executed with `poly` (and ideally compiled with `polyc`),
- do not evaluate any `.at` code at runtime,
- rely on Atlas C++ semantics via a small, auditable FFI surface,
- are sufficiently close to the original `.at` script logic to support:
  - maintenance,
  - cross-checking against the `.at` baseline, and
  - eventual formal verification arguments about equivalence (under explicit FFI contracts).

### 1.2 Non-goals (at least for the current stage)

- Reimplement Atlas’ core mathematics in SML.
- Fully verify the Atlas C++ codebase (too large).
- Immediately provide proofs of end-to-end equivalence.

Instead, we target a pragmatic story:

- **SML implements the script-level algorithms** (glue logic, enumeration, filtering, hashing, orchestration).
- Atlas C++ remains the semantic backend and is treated as an *oracle* behind **explicit specifications/contracts**.
- Formal verification proceeds top-down: prove the SML control-flow skeletons and data-structure invariants; treat Atlas primitives axiomatically at first; then gradually tighten assumptions.

## 2. Repository layout and the “replacement” architecture

### 2.1 Major directories and their roles

- `sources/`: Atlas C++ implementation (utilities/structure/gkmod/io/error, etc.).
- `atlas`: the Atlas interpreter executable (classic `.at` runtime).
- `atlas-scripts/`: the `.at` script library (the original high-level layer).
- `atlas-scripts-sml/`: the SML replacement layer:
  - translated scripts (`*.sml`),
  - support libraries and data structures (`ParamHash`, lattice/matrix utilities, etc.),
  - the Poly/ML FFI bindings and C++ shim (`ffi/`),
  - fixtures and SML-based data generators (`data/`).
- `formal/`: formalization artifacts:
  - `formal/hol4/`: HOL4 theories and goal stacks for top-down verification.
  - `formal/cakeml/`: CakeML translator experiments and refinement lemmas for hash-table/stateful components.
- `hol/`: local HOL4/CakeML toolchain checkout (ignored by git; pinned commits recorded in `HOL_TOOLCHAIN.md`).
- `doc/atlasofliegroups-docs/`: Atlas documentation mirror (Sphinx/reST sources etc.), useful for semantics and conventions when reading `.at` scripts and aligning SML ports.

### 2.2 Architectural principle: “Keep the trusted base explicit”

The essential architectural separation is:

1. **Atlas semantics** (trusted, initially): groups, parameters, normalization/finalization, unitarity tests, equivalence, contragredient/twist/cross/Cayley operations.
2. **Script-level algorithms** (to be reimplemented, then verified):
   - enumeration over KGB/lambdas/barycenters,
   - filtering and bucketing,
   - set/hashing deduplication,
   - orchestration and invariants checks,
   - tracing/logging.
3. **Bridge layer** (specification boundary):
   - a minimal C ABI shim exposing selected Atlas C++ operations,
   - a Poly/ML FFI binding layer,
   - explicit contracts about equality/hash coherences and congruence of semantic predicates.

The repository’s formalization stack follows exactly this separation:

- HOL4 proves most “algorithmic skeleton” facts over abstract primitives.
- Axioms/`CHEAT`s are used only at well-marked bridge points, with an explicit inventory (`formal/hol4/CHEATS.md`).

## 3. Poly/ML-facing Atlas API (FFI shim) and design tradeoffs

### 3.1 Why an FFI shim exists at all

Atlas is C++. Poly/ML can call C ABIs. Therefore:

- we implement a small **C ABI shim** in C++ (`extern "C"` exports),
- compile it (and enough of Atlas) into a shared library,
- bind it from SML using Poly/ML’s `Foreign` interface.

This is the key enabler: it replaces “the `.at` interpreter is the only high-level interface” with “SML can directly call Atlas primitives”.

### 3.2 The build system for the shim

FFI build helper:

- `atlas-scripts-sml/ffi/build.sh`

Key properties:

- Builds position-independent objects (`-fPIC`) and links a shared library:
  - `atlas-scripts-sml/ffi/libatlas_smlffi.so`
- Compiles selected Atlas C++ directories as PIC objects:
  - `sources/utilities`, `sources/structure`, `sources/gkmod`, `sources/io` (excluding `interactive*.cpp`), `sources/error`
- Includes a CWEB “source generation” step if needed:
  - checks for generated `sources/io/filekl*.{cpp,h}`
  - generates via `ctangle` from `sources/io/filekl.w` if missing
- Uses `-std=gnu++14` (chosen for compatibility with this codebase/toolchain in this environment).

The policy is intentionally conservative: the shim should avoid linking the interactive/front-end layer and should stay as close to “library usage” as possible.

### 3.3 C++ shim structure and error handling

Shim file:

- `atlas-scripts-sml/ffi/atlas_smlffi.cpp`

Important design points:

- Exceptions are caught and converted into an error string stored in thread-local state:
  - `atlas_last_error() : const char*` returns the last error message.
- Many exported functions return sentinel values on failure:
  - `-1`, `null`, or a textual `"-1"` result string.
- The shim uses a thread-local “last result” buffer for `const char*` outputs:
  - the returned pointer is ephemeral; SML should copy it if needed.
- The shim introduces explicit “handle” structs (opaque pointers from SML):
  - `GroupHandle` wraps Lie type / inner class / pre-root datum / involution / inner class / real reductive group and a `Rep_table`.
  - Similar patterns exist for other objects; the general strategy is “SML sees an opaque pointer; C++ owns layout and invariants”.

The shim also includes small “glue utilities” for parsing text representations:

- `parse_int_list` (whitespace-separated ints),
- `parse_int_matrix_text` (“rows cols entries…” format),
- text renderers for matrices (`int_matrix_to_text`), etc.

This “text ABI” is a recurring theme: it is robust across FFI boundaries and matches Atlas’ own textual conventions (the interpreter already uses text heavily).

### 3.4 SML bindings and lifetime discipline

SML binding module:

- `atlas-scripts-sml/ffi/AtlasFFI.sml`

Properties:

- Thin, mostly 1:1 bindings to exported C symbols (names intentionally match).
- Treats most Atlas objects as opaque “handle” types.
- Documents ownership rules:
  - functions containing `new` / `clone` allocate and must be freed via `*_free`,
  - functions returning `cString` are ephemeral.

This explicit lifetime discipline is important both for:

- correctness/performance (avoid leaks in long runs), and
- verification (well-scoped resource usage is easier to reason about at the SML level).

### 3.5 Practical pitfalls encountered and resolved

Several issues recur when moving interpreter logic into SML+FFI:

1. **Negative integer text format**
   - Poly/ML prints negative integers as `~n`, whereas Atlas parsers expect `-n`.
   - SML code that emits “Atlas text” includes helpers to normalize to `-`.
   - Example: `F4_FPP_points_compute.intToCText`.

2. **“Text as ABI” vs pointer/array ABIs**
   - Early attempts to pass arrays/pointers directly were brittle.
   - The project consistently uses whitespace-separated text for:
     - integer vectors,
     - matrices,
     - Weyl words, etc.
   - This is slower per call, but vastly simpler and more stable, and can be optimized later.

3. **Poly/ML compile exit codes**
   - Poly/ML can print “Static Errors” but still exit with status 0.
   - Therefore, compile checks should scan stdout/stderr for `Static Errors` or `error:`.

4. **C++ internal representation surprises**
   - Example documented in earlier progress: KType polynomial iteration must use `count_terms()` rather than `.size()` (some internal arrays include zero-coefficient slots).
   - This class of bug is addressed by keeping the shim small and adding targeted tests.

## 4. Translation methodology: from `.at` scripts to `.sml` modules

### 4.1 “Line-by-line” intent vs pragmatic refactoring

The user intent was: “translate `.at` to `.sml` kind of line by line,” producing SML that can run directly against Atlas C++ without the `.at` interpreter.

In practice, a strict syntactic translation is not ideal because `.at` scripts mix:

- (a) computation over Atlas objects (semantic primitives),
- (b) pure combinatorics and arithmetic,
- (c) orchestration and global mutable flags,
- (d) printing and interactive-style output conventions.

The SML port strategy is:

- preserve the **algorithmic structure** of the `.at` script,
- factor out reusable “script library” components into SML modules,
- model global `.at` flags as explicit SML refs (e.g. `FPPFlags.sml`),
- keep entry scripts as small “drivers” that just load modules and call a `run()` function,
- document each SML file with a top-level comment:
  - what `.at` file it corresponds to,
  - what is implemented vs stubbed,
  - what invariants it enforces,
  - how it should be run.

This yields a codebase that is still recognizable as a translation, but significantly more maintainable and testable than a literal syntactic rewrite.

### 4.2 Incremental development + tests as “micro-bridges”

A guiding workflow has been:

1. Add one new shim function (or extend an existing one).
2. Bind it in `AtlasFFI.sml`.
3. Add a focused Poly/ML test script in `atlas-scripts-sml/ffi/`.
4. Use the new capability in a translated module.

This reduces the risk of:

- subtle mismatches between `.at` and “SML+FFI” semantics,
- memory leaks/crashes,
- and silent API drift.

The most important integration check remains the end-to-end F4 verifier:

- `poly -q < atlas-scripts-sml/script_to_verify_F4_FPP_unitary_dual.sml`

## 5. The core deliverable: F4 FPP unitary dual verification in SML

### 5.1 What the original `.at` script does

The `.at` script `script_to_verify_F4_FPP_unitary_dual.at` is a high-value “integration verification” of a very specific pipeline:

- construct a finite set of Atlas parameters associated to “FPP facet/bottom-layer points” for a target group (here `F4_s`),
- ensure the set has the expected size (1864),
- and run a suite of consistency checks (unitary, hermitian, closures/equivalences) that certify the computed set is coherent.

This is exactly the kind of workflow that benefits from:

- typed scripting,
- a cleaner module system,
- better testability,
- and eventual formalization.

### 5.2 SML entry points and module graph

The SML replacement is:

- Entry script: `atlas-scripts-sml/script_to_verify_F4_FPP_unitary_dual.sml`
  - loads `VerifyF4FPP` and runs `VerifyF4FPP.run()`.
- Driver: `atlas-scripts-sml/VerifyF4FPP.sml`
  - constructs the group `F4_s` via `AtlasFFI.atlas_group_new_simple (#"F",4,#"s",0)`,
  - allocates a `ParamHash` for deduplicated parameter storage,
  - configures `FPPFlags` (mirroring `.at` global variables),
  - runs the compute phase:
    - `F4_FPP_points_compute.computeAllIntoParamHash (g, uhash)`
  - asserts the resulting set size is 1864,
  - runs the bottom-layer check suite:
    - `FPP_globalDirac.FPP_unitary_hash_bottom_layer_param_hash (g, uhash)`,
  - prints the initial size check and the final size, then frees resources.

This splits responsibilities cleanly:

- `F4_FPP_points_compute.sml`: “compute the candidate set” (fast generator).
- `ParamHash.sml`: “deduplicate and store handles” (data structure layer).
- `FPP_globalDirac.sml`: “check invariants on the computed set” (verification layer).

### 5.3 Fast compute phase: core algorithm (informal)

Module:

- `atlas-scripts-sml/F4_FPP_points_compute.sml`

High-level intent:

> Build the set of final Atlas parameters corresponding to the F4_s bottom-layer/FPP points, by enumerating KGB elements and their lambda families, then matching compatible barycenters gamma using a key-based constraint derived from the involution theta(x).

Algorithm sketch (as implemented today):

1. Build group facts from `AtlasFFI`:
   - rank, KGB size, splitness, number of positive roots (used to detect “looksLikeF4s” for fixture selection).
2. Acquire barycenters and lambdas:
   - for the standard `F4_s` instance, prefer loading precomputed fixtures when available:
     - `F4_FPP_barycenters.loadRatvecs()` or compute via `FPP_barycenters_fold.barycenters_all g`,
     - `F4_FPP_lambdas.loadRatvecs kgbSize` or compute via `FPP_lambdas_fold.FPP_lambdas_table g`.
   - This is a stability/performance choice; the fixtures can be regenerated from SML and serve as regression anchors.
3. For each KGB element `x`:
   - parse the involution matrix `theta(x)` from Atlas text (`atlas_group_kgb_involution_matrix_text`).
   - form `onePlus = I + theta`.
4. Pre-bucket barycenters by a key derived from `onePlus * gamma`:
   - normalize rational vectors and represent them as stable integer lists `[den, nums...]`.
   - build a hash map from “key” to indices of barycenters with that key.
   - this turns the expensive condition “(I+theta)*gamma = something” into key matching.
5. For each candidate lambda associated to `x`:
   - compute `thetaPlus = (I+theta)*lambda`.
   - compute `thetaPlusHalf = thetaPlus / 2` (as rational vector).
   - use `thetaPlus` (or its normalized key) to select compatible `gamma` from the bucket structure.
6. For each compatible `gamma`:
   - compute:
     - `nu = gamma - (I+theta)*lambda/2`
   - construct an Atlas parameter:
     - `atlas_param_new_from_lambda_nu_text (g, x, lambda, nu)` (text+den ABI),
   - normalize:
     - `atlas_param_normalise`,
   - filter:
     - standard, final, hermitian, and (optionally) unitary (controlled by `FPPFlags.Dirac_flag`),
   - insert into `ParamHash` via `ParamHash.match`.
   - free temporary handles promptly.

Notable design decisions:

- The compute phase is written to be **streaming**: temporary parameters are freed immediately; only canonical stored handles remain in `ParamHash`.
- Unitarty checks may be expensive; the code avoids re-checking if an equivalent parameter is already stored.
- The output is deduplicated using Atlas semantic equality and hash via `ParamHash` (see next section).

### 5.4 ParamHash: deduplication and stable indexing over Atlas parameters

Module:

- `atlas-scripts-sml/ParamHash.sml`

This is a small, purpose-built data structure, representing “a set of parameters with stable indexing”:

- buckets: `entry list array` (bucketed by `AtlasParam.hash_mod`),
- params: an insertion-order array of stored parameter handles,
- count: size.

Key semantics:

- `ParamHash.match`:
  - checks if an equal parameter is already present (via `AtlasParam.eq`, ultimately `atlas_param_equal`),
  - if absent, clones the parameter handle (`atlas_param_clone`) so the table owns its copy,
  - returns the assigned index.
- `ParamHash.lookup` / `contains`:
  - membership tests using bucket scan and semantic equality.
- `ParamHash.freeAll`:
  - frees all stored handles (the table owns them).

This module is central to both performance and verification:

- Performance: prevents repeated expensive unitary checks and duplicates in enumeration.
- Verification: it is a “small imperative-ish” structure with a crisp spec (“represents a set modulo semantic equality”), making it a natural target for CakeML proofs and for bridge contracts in HOL4.

### 5.5 Bottom-layer verification checks (global Dirac pipeline)

Module:

- `atlas-scripts-sml/FPP_globalDirac.sml`

This module ports/adapts the “global Dirac” bottom-layer checker pipeline used by the original `.at` scripts. It treats a computed set of parameters as a `param_set`:

```sml
type param_set = {list: unit -> param list, contains: param -> bool}
```

and then runs checks that mirror the `.at` script:

- **standard/final sanity**: all parameters are standard and final (`atlas_param_is_standard`, `atlas_param_is_final`).
- **lambda-table consistency** (F4-specific): for each parameter `p`, `lambda(p)` must appear in the computed `FPP_lambdas_fold` table for its `x`.
- **twist equivalence**: each parameter is equivalent to its twist (`atlas_param_twist` and `atlas_param_equivalent`).
- **hermitian**: each parameter is hermitian (`atlas_param_is_hermitian`).
- **unitary (if Dirac enabled)**: each parameter is unitary (`atlas_param_is_unitary`), possibly with additional pruning logic.
- **unitary-dual closure**: closure under contragredient (`atlas_param_contragredient`) checked using the `contains` method of the backing set.
- **compact special-case**: the original `.at` pipeline treats compact groups differently (rho seeding); the HOL4 spec models this case distinction explicitly, and the SML checker follows that structure.

The intent is that `FPP_globalDirac` remains a checker: it should not “silently fix up” the set, but only validate invariants (raising on failure).

### 5.6 Data fixtures and SML regeneration

The SML side ships fixtures under `atlas-scripts-sml/data/` (not reproduced in this report) that act as regression anchors:

- `F4_FPP_barycenters.txt`
- `F4_FPP_lambdas.txt`
- `F4_FPP_points.txt`

Critically, the repository now includes SML-based generators so these fixtures can be regenerated without `.at` scripts:

- `atlas-scripts-sml/data/gen_F4_FPP_aux_data_sml.sh` (barycenters + lambdas)
- `atlas-scripts-sml/data/gen_F4_FPP_points_sml.sh` (points)

The SML-first generators support a safe “write `*.new` unless explicitly overwriting” policy, keeping diffs stable.

Practically, the verifier can run “from scratch” in the sense of not calling `.at` scripts. The fixture usage is a choice (stability/performance) rather than a semantic dependency, and the project’s direction is to keep fixtures as regression tests rather than as required inputs.

## 6. The slow completeness checker: translation and intended use

### 6.1 Purpose and constraints

The `.at` “simpler” checker is explicitly inefficient: it brute-force enumerates a large product domain of triples `(x, lambda, gamma)` and checks that any unitary final term it discovers is present in the known “fast” unitary set.

Because the brute-force domain is extremely large, **it is not intended to be executed to completion** in this environment (multi-hour).

Nevertheless, translating it is valuable because:

- it provides a “completeness check” semantics that can be formalized,
- it supplies a clean specification target: “no missing witness exists”,
- it forms the basis of the end-to-end equivalence theorem structure in HOL4.

### 6.2 SML translation

Module:

- `atlas-scripts-sml/SimplerVerifyF4FPP.sml`

Key characteristics:

- The translation explicitly corrects a naming pitfall from the `.at` script:
  - in the original `.at`, `nu` may refer to a barycenter gamma;
  - in the SML port, `nu` is consistently constructed as:
    - `nu = gamma - (I+theta(x))*lambda/2`
  matching the fast compute module’s construction.
- Domain enumeration is implemented as a streaming iterator `for_domain` rather than materializing the full domain list.
- The per-triple check:
  - constructs a parameter from `(x, lambda, gamma)`,
  - selects the first final term (freeing intermediates),
  - checks unitarity,
  - checks whether it is missing from the known hash (`ParamHash.lookup < 0`),
  - frees handles.
- The module provides:
  - `runSlow()` (full enumeration; should not be run in practice),
  - `runFast(maxX, maxLambdasPerX, maxGammas)` (bounded sampling).

Entry script:

- `atlas-scripts-sml/simpler_script_to_verify_F4_FPP_unitary_dual.sml`

is intentionally disabled by default to prevent accidental long runs.

### 6.3 How this connects to the formal story

At the specification level (see `VERIFY_ESTIMATE.md`), the slow checker supports a theorem of the form:

> If the slow checker returns “0 misses”, then the slow-semantics set `U_slow` is contained in the fast set `U_fast` (completeness relative to the chosen domain).

The formal development makes this precise using:

- `missing_witness` predicates (and modulo-`atlas_eq` variants),
- list-model checkers like `check_domain_fun`,
- domain correctness facts showing that the enumerator covers exactly the intended set of triples.

The key point is that slow-checker execution is *not* the proof: it is evidence and/or the basis for bridge obligations. The proof is staged and aims to justify the meaning of “0 misses” in a mathematically clean model.

## 7. Additional SML ports and reusable library growth

The project is no longer “just the F4 verifier”: a large portion of the `.at` library has been translated into SML files under `atlas-scripts-sml/`. Not all are complete; many are scaffolds or partial ports. However, several important supporting areas are functional enough to serve as building blocks for broader translation.

This section highlights key pieces relevant to future work and to the project’s “replacement interpreter” thesis.

### 7.1 Script orchestration layer

Most translated scripts are structured as:

- a module file `Foo.sml` containing `structure Foo = struct ... end`,
- a runner `foo_main.sml` / entry script that loads dependencies and calls `Foo.run()` (or similar).

This matches Poly/ML usage (`use "..."`) while also supporting `polyc` compilation via a dummy `main`.

### 7.2 Representations and unitarity harness

From earlier reports, the SML side includes:

- translated spherical unitarity point tables (`unitary.sml`) for `F4`, `D4`, `E7`,
- a unitarity harness (`test_unitarity.sml` + `test_unitarity_main.sml`) that constructs parameters and checks unitarity (often via hermitian-form purity),
- representation constructors in `representations.sml` (minimal principal series, finite-dimensional, discrete series scaffolding, etc.),
- cross-orbit utilities (`cross_W_orbit.sml`) with BFS-style orbit search,
- dominance helpers (`FromDominant.sml`, `WeylWord.sml`) that connect to Atlas operations.

These modules are important for “scaling up translations”: many `.at` scripts rely on these primitives.

### 7.3 Pure combinatorics ports: Springer theory and nilpotent orbits (classical types)

Recent work has expanded the “pure combinatorics” part of the SML library substantially. These ports are intentionally designed to avoid the Atlas interpreter and avoid dependence on Atlas C++ “nilpotent orbit object” APIs that are not yet exposed via FFI.

Key files include:

- `atlas-scripts-sml/combinatorics.sml`
  - Provides permutation utilities and a large set of partition/combinatorics functions.
  - Recent additions include:
    - 2-core / 2-quotient decomposition (`core_quotient_2`, inverse, and helpers),
    - parity-restricted partition generators,
    - dominance order and validity/parity predicates,
    - helpers used by classical Springer correspondence code.
- `atlas-scripts-sml/springer_table_BC.sml`
  - Partial port of `springer_table_BC.at`:
    - diagram → partition conversions for types B/C,
    - Springer map diagram/partition → bipartition (Weyl-group irrep parameter),
    - B/C duality adjustments (`B_adjust`, `C_adjust`, `B_to_C_dual`, `C_to_B_dual`),
    - generators of valid partitions for B_n and C_n.
  - Explicitly does *not* yet implement the Atlas-facing “ComplexNilpotent” layer.
- `atlas-scripts-sml/springer_table_D.sml`
  - Partial port of `springer_table_D.at`:
    - diagram → (partition, flip) reconstruction,
    - Springer correspondence in type D to “split/unsplit” irrep datatypes,
    - D-duality on partitions.
  - Again, Atlas-facing nilpotent orbit objects and stratified diagrams are not yet bound.
- `atlas-scripts-sml/W_reps_type_BC.sml`
  - Partial port of `W_reps_type_BC.at`:
    - orbit partition ↔ bipartition ↔ Lusztig symbol conversions,
    - specialness predicates,
    - hook-length dimension formula for type-B/C Hecke algebra representations.
- `atlas-scripts-sml/nilpotent_orbit_partitions.sml`
  - Partial port of `nilpotent_orbit_partitions.at`:
    - partition classification of complex nilpotent orbits in classical types A–D,
    - dominance/closure computations,
    - semisimple-element vectors from partitions.
  - Not yet connected to Atlas’ `ComplexNilpotent` representation.

These pure combinatorics modules serve two roles:

1. They replace parts of the `.at` library that are logically independent of Atlas C++ objects.
2. They reduce the eventual verification burden by moving more work into a pure functional core that can be reasoned about directly in HOL/CakeML without FFI assumptions.

- build in `formal/hol4` and `formal/cakeml` via `Holmake`.

### 8.2 What “equivalence” means in this project

The repository’s guiding statement (from `VERIFY_ESTIMATE.md`) is:

- the fast program (`VerifyF4FPP.sml`) computes a candidate set `U_fast` and checks invariants on it;
- the slow program (`SimplerVerifyF4FPP.sml`) defines an enumeration domain `D_slow` and searches for “missing witnesses”.

So “equivalence” is not literal behavior equality; it is set-theoretic:

1. **Soundness**: every element produced by the fast program is a genuine unitary final term witnessed by some triple in the intended domain.
2. **Completeness (relative to the slow domain)**: if the slow checker finds no missing witness, then any unitary final term witnessed by a triple in the domain must already be represented in `U_fast`.

Because the implementation uses Atlas semantic equality (`atlas_param_equal`) rather than HOL equality of pointer identities, the formalization is primarily expressed modulo an abstract relation `atlas_eq`, leading to:

- `set_atlas_eq` and `mem_set_atlas_eq` predicates,
- contract bundles like `atlas_hash_eq_ok` ensuring hash/equality coherence.

### 8.3 HOL4 development: goal-driven decomposition with explicit bridges

The HOL4 development lives in `formal/hol4/` and is documented by:

- `formal/STRATEGY.md` (narrative of the refinement structure),
- `formal/hol4/GOALS.md` (goal checklist; what remains),
- `formal/hol4/CHEATS.md` (precise inventory of current `CHEAT`-tainted obligations).

The overall approach is:

- define abstract semantics of the two programs as sets and predicates,
- prove “algorithmic skeleton” lemmas about list folds, domains, and set transforms,
- isolate all links to “real execution” behind named bridge predicates,
- state all required FFI/equality/hash contracts explicitly in one place,
- allow proofs to be “cheated” at first *only* at bridge boundaries.

#### 8.3.1 Spec layer (abstract semantics)

`formal/hol4/F4FPPVerifySpecScript.sml` defines:

- abstract types (`group`, `ratvec`, `param`, `triple`),
- abstract primitives (e.g. `mk_param`, `first_final_term`, `is_unitary`),
- domain sets (`KGB`, `FPP_lambdas`, `AllBarycenters`) and derived slow domain `D_slow`,
- slow semantics `U_slow`,
- a completeness relation `complete_rel` defined via absence of missing witnesses,
- and proves basic set-theory lemmas (e.g. `complete_rel_imp_subset`).

There are parallel “modulo-`atlas_eq`” variants that define:

- `mem_atlas_eq`, `set_atlas_eq`, and closure-based membership.

#### 8.3.2 Algorithmic skeleton layer (slow checker control-flow)

`formal/hol4/F4FPPVerifyAlgScript.sml` models the slow checker as a pure list function:

- `check_domain_fun g U_fast ts : num`

and proves equivalences of the form:

- `check_domain_fun = 0` ↔ “no missing witness in `ts`”
- `check_domain_fun = 0` ⇒ `complete_rel` (under domain correctness assumptions)

This isolates the ML loop reasoning from the Atlas semantics.

#### 8.3.3 Fast program decomposition: domain pruning, witness tracing, and ParamHash obligations

The fast program’s logic is decomposed into obligations that match the implementation structure:

- identify what triples are considered (`D_fast`, possibly as a pruned subset of `D_slow`),
- show every stored parameter has a witness triple (witness trace),
- show ParamHash represents exactly the set (contains/list soundness + completeness).

The goal stack provides multiple routes:

- a “refined-main” route emphasizing domain/list structure and bottom-layer predicates,
- an “obligation-stack” route emphasizing ParamHash state, traces, and modulo-`atlas_eq` reasoning.

#### 8.3.4 Bottom-layer checks as set-level predicates

`formal/hol4/F4FPPBottomLayerGoalsScript.sml` captures the bottom-layer checks performed by `FPP_globalDirac.sml` as *set predicates*:

- `standard_final_ok`,
- `lambda_table_set_ok`,
- `twist_equiv_ok`,
- `hermitian_ok`,
- `unitary_if`,
- `dual_closed`,
- and the combined `bottom_layer_total_ok` with a compact-group special case.

There are corresponding modulo-`atlas_eq` variants in:

- `formal/hol4/F4FPPBottomLayerGoalsAtlasEqScript.sml`.

#### 8.3.5 Explicit Atlas/FFI contract inventory

The “trusted base” assumptions about Atlas equality/hash/congruence are centralized in:

- `formal/hol4/F4FPPVerifyAtlasFFIContractsGoalsScript.sml`

This introduces a bundled predicate (informally):

- `atlas_hash_eq_ok` (equivalence + hash coherence + range + clone behavior),
- plus congruence/stability of semantic predicates under `atlas_eq`.

The fact that “contracts hold” is currently an axiom (a deliberate placeholder) tracked in:

- `formal/hol4/F4FPPVerifyAtlasFFIContractsCheatsGoalsScript.sml`
and summarized in `formal/hol4/CHEATS.md`.

#### 8.3.6 Bridge predicates: “program succeeds ⇒ obligations”

The key remaining “hard” bridge is:

> showing that successful execution of the Poly/ML programs implies the abstract obligations in HOL4.

These are currently isolated behind named `cheat`ed lemmas in:

- `formal/hol4/F4FPPVerifySMLBridgeCheatsGoalsScript.sml`,
- plus specialized bridge layers for compute-phase, slow program decomposition, and bottom-layer checks.

Structurally, these files are valuable already: even with `CHEAT`s, they provide a *precise checklist* for what a future CakeML/translator proof (or another execution model) would need to establish.

### 8.4 CakeML side: translator playground for pure/stateful subcomponents

The CakeML development in `formal/cakeml/` is intentionally a “sandbox” for proving correctness of smaller pieces that are central to the overall equivalence argument, especially stateful structures like ParamHash.

Key files:

- `formal/cakeml/F4FPPCheckDomainProgScript.sml`
  - translates a minimal pure checker for `check_domain_fun`.
- `formal/cakeml/ParamHashProgScript.sml`
  - translates a monadic “ParamHash-like” structure using the monadic translator.
- `formal/cakeml/ParamHashGoalsScript.sml`, `ParamHashRefinementGoalsScript.sml`, etc.
  - record top-down refinement goals connecting the monadic operations to a pure-state model and then to a set-interface view.

The strategic intent is:

1. Prove robust invariants and representation lemmas for the hash-table model inside HOL/CakeML (no FFI assumptions).
2. Reuse those lemmas as “discharged obligations” in the HOL4 goal stack (which already has clean interfaces for ParamHash obligations).
3. Keep the Atlas-facing semantics as explicit assumptions until there is a realistic plan to validate or shrink them.

## 9. Current status: what is completed vs what remains

### 9.1 Completed (high-confidence milestones)

**SML execution layer**

- Poly/ML can call Atlas via `libatlas_smlffi.so`.
- The SML side can construct `F4_s` groups and build/normalize/filter parameters.
- The F4 verifier runs and reports the expected size (1864) and passes the bottom-layer checks.

**Translation of the most important workflow**

- `script_to_verify_F4_FPP_unitary_dual.at` has an SML counterpart that is runnable and does not depend on `.at` scripts.
- The “slow script” has an SML translation suitable for specification and partial sampling.

**Formalization scaffolding**

- HOL4 has a detailed top-down goal stack, with explicit bridge points and a maintained cheat inventory.
- ParamHash state representation lemmas exist and are proved in HOL4 both:
  - under the simplifying assumption `atlas_eq_is_hol_eq`, and
  - in a more realistic modulo-`atlas_eq` style under `atlas_hash_eq_ok`.
- CakeML translator artifacts exist for the slow checker skeleton and for ParamHash-like models, with refinement lemmas proved in the sandbox setting.

**Pure combinatorics growth**

- Classical partition-based nilpotent orbit classification, Springer combinatorics for types B/C/D, and symbol/bipartition conversions have substantial pure-SML ports.

### 9.2 Still pending / open work (as of this report)

**FFI surface evolution**

- Many `.at` scripts depend on interpreter-provided composite operations not yet exposed through the shim. The current strategy is to add new shim functions only when needed and to keep them semantically high-level.
- Nilpotent orbit objects, stratified diagrams, and other “ComplexNilpotent” APIs are not yet accessible via the current Poly/ML FFI layer; existing SML Springer/nilpotent-orbit files therefore stop at the partition/diagram combinatorics.

**Translation completeness across `atlas-scripts/`**

- While many `.at` files have corresponding `.sml` files, the completeness varies:
  - some are fully functional ports,
  - some are partial ports (functional core + stubs),
  - some are scaffolds intended to compile but not yet implement full behavior.
- The translation effort is therefore best viewed as “a growing SML script library” rather than “complete 1:1 replacement of all `.at` scripts” (yet).

**Formalization bridges**

The HOL4 development has a clear separation between:

- “OK” proof content (list/set reasoning, decomposition lemmas),
- and “bridge lemmas” that connect real execution to abstract obligations.

The remaining heavy pieces are largely those bridges:

- connecting `VerifyF4FPP` success to fast semantic obligations,
- connecting `SimplerVerifyF4FPP` success to slow domain correctness and 0-miss semantics,
- connecting Poly/ML `ParamHash` behavior to the abstract ParamHash state model (or to the CakeML model),
- formalizing and/or validating `atlas_ffi_contracts` (or explicitly accepting it as trusted).

These are documented as explicit checklists in `formal/hol4/GOALS.md` and `formal/hol4/CHEATS.md`.

## 10. Risks, constraints, and realistic outlook

### 10.1 The major technical risk: Atlas semantics and the FFI trust boundary

Any end-to-end equivalence theorem necessarily depends on substantial Atlas semantics:

- parameter construction,
- normalization/finalization,
- unitary predicates,
- semantic equality,
- and group data (KGB involutions, etc.).

The project’s current plan is realistic:

- treat these as abstract primitives with explicit contracts first,
- prove the “glue logic” rigorously,
- and only later decide how far to push in shrinking the trusted base.

There is no credible path to fully verifying Atlas C++ in the near term; the best achievable results will likely look like:

> “Assuming the Atlas FFI functions satisfy the stated contracts, the SML programs implement the stated specs; and the slow checker implies completeness relative to the domain.”

This is still a valuable theorem in practice, because it identifies exactly what must be trusted and what has been verified.

### 10.2 Performance risks and mitigation

Two performance-related constraints shape the design:

- brute-force domain enumeration is extremely large (hence the slow checker is non-executable as a routine test),
- the FFI boundary is relatively expensive (hence caching and bucketing in SML is important).

Mitigations used:

- gamma bucketing by key to avoid `O(|gammas|)` scans for every lambda,
- deduplication early to avoid repeated expensive unitary checks,
- fixtures/regeneration to keep stable regression behavior while allowing “from scratch” computation when needed,
- sampling mode for the slow checker.

### 10.3 Maintainability risks and mitigation

Translating scripts line-by-line can produce fragile code if not managed carefully. The SML work mitigates this with:

- consistent file-level documentation blocks (what it corresponds to, what it does),
- a stable “thin FFI + thicker SML library” structure,
- a strong preference for small, named helper functions over anonymous script fragments,
- tests that pin down semantics of each new shim binding.

## 11. Roadmap (engineering and formalization), with staged refinement

This roadmap is consistent with the structure in `VERIFY_ESTIMATE.md` and `formal/STRATEGY.md`, but updated to reflect the current artifact stack.

### 11.1 Engineering roadmap (SML translation and bindings)

1. **Keep the FFI surface small and compositional**
   - add bindings when needed by additional script translations,
   - prefer semantically meaningful operations over exposing internal C++ object graphs,
   - keep memory ownership explicit and test each new binding.
2. **Continue translating high-value `.at` scripts into SML**
   - prioritize scripts that:
     - are verification-critical,
     - or provide frequently used library functionality in `.at`.
3. **Reduce reliance on fixtures where practical**
   - keep fixtures as regression anchors,
   - but ensure any fixture can be regenerated from SML-only code paths.
4. **Extend nilpotent-orbit and Springer layers as bindings become available**
   - decide whether to:
     - expose nilpotent orbit objects through the FFI, or
     - keep the orbit layer purely combinatorial where possible.

### 11.2 Formal roadmap (HOL4/CakeML), “proofs can be cheated but structure must be precise”

The formal work is explicitly structured to support gradual strengthening:

Stage A — *Assumption-heavy, structure-correctness*:

- Prove that:
  - the slow checker computes exactly the “missing witness” count over the intended domain list,
  - the fast program’s compute phase produces a set `U_fast` that is witnessed by the intended domain (soundness),
  - the bottom-layer checker enforces the stated invariants.
- Treat Atlas primitives and FFI contracts as assumptions.

Stage B — *Verified data structures and traversal skeletons*:

- Discharge ParamHash representation and invariant obligations in CakeML/HOL,
- connect those to HOL4 obligations (set view of hash-table, modulo-equality reasoning).

Stage C — *Domain/pruning completeness arguments*:

- Make the fast pruning predicate explicit (`fast_considers`) and prove it does not exclude relevant unitary final terms (or state as an assumption if that is where Atlas semantics is unavoidable).

Stage D — *Optional shrinking of the trusted base*:

- Decide how far to go:
  - keep Atlas contracts axiomatic,
  - validate them empirically,
  - or attempt deeper verification of specific sub-primitives.

The key deliverable in the near term is not a fully formal proof, but a well-specified and refined collection of theorems/definitions that make “what must be proved” explicit and modular. This is exactly what the HOL4 goal stack provides today.

## 14. Closing remarks

The technical thrust of this project is now clear and supported by real artifacts:

- An SML execution layer exists and is demonstrably capable of replacing important `.at` scripts.
- The F4/FPP verification pipeline is running end-to-end in SML, using Atlas C++ semantics via an FFI shim.
- The codebase has been shaped into a reusable SML “script library” rather than a single one-off port.
- A formal verification story has been designed with unusually explicit refinement structure and a maintained cheat/assumption inventory.

The next phase is primarily about scaling:

- engineering scaling (port more `.at` scripts with minimal new FFI surface),
- and proof scaling (turn “bridge obligations” into formal theorems or justified assumptions, starting with pure data structures and then addressing program-success bridges).

Both are tractable within the established structure: the current repository already contains a roadmap, a decomposition into small obligations, and enough working code to keep the formal effort grounded in real computation rather than toy models.
